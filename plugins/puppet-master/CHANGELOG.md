# Changelog

All notable changes to puppet-master are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- A `puppet-master` skill: one Claude session hands your jobs to the Claude sessions you already have open, and starts a background worker only when none of them is free. Each session gets one job. The master relays their questions to you one at a time, quoting your own words, and gets a session compacted only between tasks once it is measured at 30% of its context or more: a background worker by itself, while your own window is left to auto-compact unless you ask for `/compact` lines to paste. It closes background workers when their jobs are done. It runs only when you type `/puppet-master:puppet-master`. It needs Node.js 20 or newer and a setting of your own first. See [Run background workers](docs/manual/use/run-background-workers.md).
- `puppet-master` keeps one session as an analyst. It reads the day's transcripts of the sessions you named, records what went wrong with evidence, with anything that looks like a secret blanked, and at the end of the day proposes changes for you to approve, reject or defer. It never changes the plugin itself.
- A plugin option, `puppet_logs_dir`: where the analyst keeps its logs. Leave it empty to use the plugin's data folder.
- `puppet-master` shows each session's model and effort, and every job names a tier: `creative` (an Opus model at high effort or more) or `mechanical` (another model at medium effort or less). When a session doesn't match and its mod is on, Claude switches that session to the right model and effort itself (`puppet switch`), for that session only and without touching your settings; your open windows get the work before a background worker does. The switch lasts through compactions and clears until it is reset. The session's status line, and its own answer when asked, keep naming the model it started with; the mod pins its own line under the prompt, `puppet-master: switched to <model> <effort>`, and `puppet list` shows the one in use. Where the mod isn't on, Claude takes another window or starts a background worker on the right model and effort, or, if you want that window for the job, gives you session-only lines to paste: `/model`, then `s` on the model's row, and `/effort`, then `s`. A typed `/model <name>` or `/effort <level>` would save your default for every new session. A background worker it starts gets the tier's model and effort from the start.
- `puppet-master` gives every session's context in tokens and as a share of a 1,000,000-token window (or the window you set in `PUPPET_CONTEXT_WINDOW`), never as a share of the size where a session once auto-compacted. Its 30%, 40% and 50% lines are 300,000, 400,000 and 500,000 tokens. A finished session over 30% is cleared through its mod where that is on, else you get its `/clear` line.
- `puppet --help` prints the usage. The master runs each `puppet` call as its own command, so a refusal never reads as part of another call's success.
- A worker's brief names the services, tools and device state the job needs, as the master checked them, and the worker checks them first. It also carries the project's own standards and, when another session commits the work, asks for the changed paths and a draft commit message. Before its `FINAL:` the worker stops its servers and background shells and closes the shared browser. It asks before touching a coupled file outside its scope, reads back its progress file, sends a progress line at least every 20 minutes while a long process runs, ends a probe session with the helper's `close`, and never opens a seed, config or env file to read a credential.
- Every brief carries the template's lines itself: `spawn` refuses a brief file that does not end with the template's last line. The master restates the job's shape in your words, tells a worker to wait for "go" only while your decision is open, gives full paths, looks at a visual deliverable before sending you its link, and checks your device before recommending a route that depends on it.
- `puppet-master` can give a finished session another job while it is under 30% of its context window, add a follow-up to the job a session holds, reopen a job closed too early, and can run two jobs in one repository when each names the folders it writes and only one of them runs git.
- A `puppet-master` worker's brief names the kind of deliverable (code, a document or a browser run), which the worker states back first, the local state it would otherwise stop to ask about, and the writes you can approve in its window up front. It reminds the worker that files its tools write by default count against its write scope, and that after a compaction it takes its place from git, not from the summary. It also reports cache folders a formatter hook leaves behind, runs multi-line scripts from a file instead of heredocs, and, when it may not run git, gets the git facts it needs in the brief. A worker never stashes, resets or switches branches over your uncommitted edits, never prints a credential, uses the browser only while it holds it, runs tests with a temp folder whose path has no spaces, and is told the values you already decided so you aren't asked twice. When it is blocked, you are asked once, with the exact command.
- `puppet-master` remembers a closed session by name and prints its resume command when you mention it again. It closes a job in the same turn the session reports it done, and marks a session that reported done while its job is still open. It checks a question's premise before asking you, re-reads what a brief claims before sending it, and offers its own `/compact` line once when it reaches 40% of its window. `list` shows a session with no known window as `?%` instead of failing. Several masters can run on one machine, each with its own `--group`: its own sessions, logs and proposal ids.
- A mod that lets a session compact itself, or clear itself, when the master asks, so you don't paste `/compact` and `/clear` lines or move work to a background worker. It does nothing in a session until you switch it on: a window you open asks once at start (suggesting yes), and a background worker is switched on only by the master, after you said yes. The master compacts an idle session with a focus it writes from the job, and clears only a worker whose job is finished, never itself, the analyst or a session with an open job. The new `self_compact` option is `ask` by default, `on` or `off` (`off` beats the master). `puppet list` shows each session's `mod` state, and the new `compact`, `clear` and `--self-compact` are in [Commands](docs/manual/reference/commands.md). It needs Claude Code 2.1.287 or newer; where the mod isn't on, the old routes (`cycle`, auto-compaction, a line to paste) stay. See [Run background workers](docs/manual/use/run-background-workers.md#let-sessions-compact-themselves).
- The analyst's day starts at 05:00, so work past midnight stays with its day (`PUPPET_DAY_START_HOUR` changes the hour). It also records your answers to Claude's question dialogs, and no longer logs an idle notification as an empty message.
- The sessions' questions come to the master's window: a worker never asks you in its own window, you set its window to accept-edits once when its job starts, and only an irreversible step (a delete, a push, a Railway write) still shows a permission prompt there. The master runs `list` before each reply and tells you first when a session is waiting on you. It also does a service's steps itself when it holds the tools, lists what a deploy or merge approval leaves out, dates any quote from an earlier day it passes on, and names yesterday's open items in the day's first status.
- A busy worker that passes the line is asked to pause at its next part boundary, compacted with a focus, and told to continue. A worker also pauses and says so past about 150k tokens.
- A worker's brief now forbids `cd <dir> && …` chains, `sed -i` and any git command in a no-git job, and forbids running a denied command again in another shell, form or in parts. A test's temp folder goes under the logs folder and is deleted when the job ends; build output stays in a gitignored folder in the repository.
- `assign --extend` accepts `--git`, keeps the job's git flag when neither `--git` nor `--no-git` is given, and no longer repeats a label.
- `--scope` takes an absolute folder outside the checkout (a temp plans folder). A job that writes only outside the checkout does not count against the one-editor-per-checkout lock; an absolute folder inside the checkout is refused, so the lock still sees it.
- `puppet-master` measures a working worker each time it relays that worker's message and at each `FINAL:`, asks a busy worker at 30% or more to pause at its next part boundary, compacts it only once its idle notice arrives, and clears a finished window whose mod is on even with no next job queued.
- `puppet-master` runs a read-only design pass before it relays a design, and puts a worker's recommendation to you as the worker's, with the simplest change beside it. A worker's question always reaches you, and Claude never answers it as its own call. It names the open question a short answer fits, gives each open question an id (A1, A2), acts on every instruction in your turn (a "go" starts the job at once) and, when a job ends, starts the items you already approved.
- A step a worker's permission check is likely to refuse, or that auto mode would refuse outright (an external write, a push), reaches you before the job starts as a `!` line for the worker's window. The worker's brief says such a step is never the worker's to run: it tells the master it has reached it and waits.
- A question about a repository is a read-only job for a session, even after `finish`, and a standing rule you state for a team becomes a proposed change in that repository, never a memory. A brief names the host, database and test account of a live check (never a password) and puts a git ref it names in the worker's preconditions. A worker quotes only output it ran, marks a figure it inferred, lists the scratch folders it made, and never creates, edits or reads a credentials file: the file is copied from its example by a shell command, or you get a `!` line.

### Changed

- The `puppet-master` skill keeps only what the master needs on every turn in `SKILL.md` (about 220 lines instead of 504), and holds the rest in `skills/puppet-master/references/`, one file per moment, moved word for word with every rule number and section name kept. After a compaction Claude Code re-attaches only the first 5,000 tokens of a skill, which cut the old file inside "When a job ends"; `SKILL.md` now tells the master to read itself again after a compaction of its own and lists, in a "Files to read, and when" table, which file to read when. Where each section went: On start to `on-start.md`; the detail of rules 3, 4, 5 and 12, "A design to relay" and Chained jobs to `jobs.md`; Briefs and "A quote from an earlier day" to `briefs.md`; the relay bullets on blocked workers, `!` lines, outside services, deploy approvals and the user's device to `approvals.md`; the detail of rules 7, 9 and 10 (the pause pattern, the mod, the user's own session) to `context.md`; the helper table to `helper.md`; Wrap-up to `wrap-up.md`; `setup-prerequisites.md` moved into `references/`. A test fails a `SKILL.md` body over 300 lines and a reference file over 200, and the plugin's `AGENTS.md` says where new skill text goes. The analyst's proposals now name their home, so you approve where a change goes together with the change. A master that was already running keeps the text it read at its start: type `/puppet-master:puppet-master` again at a task boundary to load the new layout.

### Fixed

- A session you rename keeps its job record under the new name instead of getting a second, `unknown` one that refused `assign --reuse` and `clear`.
- A session that only read its brief and replied counts as clean when it is adopted.
- Adopting a session that is already in the list keeps its job and state; it only updates its role, window and mod role. `clear` on a worker whose mod has no role file now says to adopt it again with `--role worker`.
- A session waiting on a dialog counts as busy for `cycle` and for the one-editor-per-checkout lock, as it already did for `compact` and `clear`, and `list` shows it as `waiting`.
- `puppet list --name <window>` finds a window you opened that nobody adopted, as the other commands already did, so the master's start no longer fails on its own window. A command that finds no session by that name now lists the live ones.
- The helper says "switched" once the mod acknowledged the switch, and its line now says the mod's line under the prompt names the switch while the status line and the session's own answer name the launch model.
- `puppet list` marks a background worker whose process is gone as `dead` (it has no process id in the session list): `compact`, `cycle` and `clear` refuse it, and `close` removes it without stopping it first. `close` retries a `stop` that fails because the background service is restarting, after 2, 4 and 8 seconds, and then says to run `close` again in a minute instead of leaving a manual `claude rm`.
- The analyst's brief now says what an evidence id is: the `id` field of an events.jsonl line, such as `6d3e35df:249`, never the line number of the file, which `finding` refuses.
- `puppet switch` refusing a busy session now says that the session keeps its current model and effort, and to run the same switch again once `puppet list --name <session>` shows it idle. The master tells you at once that the session was not switched, so you don't find out by looking.

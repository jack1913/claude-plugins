## Design Once, Adapt the Form

- Design the app's anatomy once and let each platform express it: iPhone is a narrow, vertical view, Mac a wide canvas, and iPad sits between the two ([WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/))
- Keep what people have learned. Grouped content stays grouped as the layout changes, an action keeps its symbol on every device, and tab bars, segmented controls and sidebars show selection and state the same way ([WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/))
- Treat the tab bar and the sidebar as one navigation element that grows with the canvas ([WWDC25 219](https://developer.apple.com/videos/play/wwdc2025/219/)). A `TabView` with `.tabViewStyle(.sidebarAdaptable)` shows a bottom tab bar on iPhone, a top tab bar that can turn into a sidebar on iPad, a sidebar on Mac, and an ornament on visionOS, with a sidebar there for the secondary tabs in a `TabSection` ([SwiftUI: sidebarAdaptable](https://developer.apple.com/documentation/swiftui/tabviewstyle/sidebaradaptable)). Tabs move between sections and never perform actions ([HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars))
- A tab with the search role sits apart at the trailing end of the tab bar ([Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass), [HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)), and a searchable tab view uses it for search ([SwiftUI: TabRole.search](https://developer.apple.com/documentation/swiftui/tabrole/search))

```swift
struct RootView: View {
    var body: some View {
        TabView {
            Tab("Library", systemImage: "books.vertical") {
                LibraryView()
            }
            Tab("For You", systemImage: "heart.text.square") {
                ForYouView()
            }
            Tab(role: .search) {
                SearchView()
            }
        }
        .tabViewStyle(.sidebarAdaptable)
    }
}
```

## Hit Targets and Control Size

HIG Accessibility gives each platform a default and a minimum control size ([HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)):

| Platform | Default | Minimum |
|---|---|---|
| iPhone, iPad | 44x44 pt | 28x28 pt |
| Mac | 28x28 pt | 20x20 pt |
| Vision Pro | 60x60 pt | 28x28 pt |

- Keep every control at least at its platform's minimum. For buttons, HIG Buttons asks for a hit region no smaller than 44x44 pt, or 60x60 pt on visionOS ([HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [HIG: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons))
- Space counts as much as size: padding around controls is in `hierarchy-layout.md` → Spacing, and the clearance around visionOS gaze targets in `swift:swiftui` → `visionos.md` → Input and hover

## iPhone

- **Navigation:** a tab bar floating on glass at the bottom of the screen (at the side on iPhone Duo's outer display; see iPhone Duo below). Keep it visible in every section (a modal view may cover it), keep the tabs few enough that none spills into a More tab, and never disable or hide a tab; if a section is empty, say why. Label each tab, in one word where possible, and prefer filled symbols ([HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars))
- **Scrolling:** the tab bar can shrink while people scroll (`tabBarMinimizeBehavior(_:)`) and expands again when they scroll back ([Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass), [HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)). An accessory above it holds only features that persist across the app, such as playback; an action for one screen stays with that screen's content ([WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/))
- **Split views:** they need width, so prefer them in regular width only ([HIG: Split views](https://developer.apple.com/design/human-interface-guidelines/split-views)); on iPhone a `NavigationSplitView` folds its columns into a single stack ([SwiftUI: NavigationSplitView](https://developer.apple.com/documentation/swiftui/navigationsplitview)); on iPhone Duo's inner display it expands side by side (see iPhone Duo below)
- **Toolbars:** room for the essential actions only, with the rest in a More menu (the system overflow menu on iPhone Duo, see below); a large title that shrinks to a standard one as content scrolls helps people keep their place ([HIG: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)). Keep the system Back and Close buttons and their symbols rather than text labels ([HIG: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars))
- **Inspectors:** `inspector(isPresented:content:)` presents as a sheet in compact width ([SwiftUI: inspector(isPresented:content:)](https://developer.apple.com/documentation/swiftui/view/inspector(ispresented:content:)))
- **Sheets:** one scoped task each. Support the medium detent when the top half of the content is enough, as in a share sheet, and keep writing tasks at full height; show a grabber on a resizable sheet; let people swipe down to dismiss, and confirm first if they would lose changes. In a single-view sheet, Cancel sits on the leading side of the top bar and Done on the trailing side ([HIG: Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets))
- **Long tasks:** video, photos, the camera and multistep editing get a full-screen modal view ([HIG: Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets), [HIG: Modality](https://developer.apple.com/design/human-interface-guidelines/modality)), `fullScreenCover(isPresented:onDismiss:content:)`, which doesn't exist on macOS ([SwiftUI: fullScreenCover(isPresented:onDismiss:content:)](https://developer.apple.com/documentation/swiftui/view/fullscreencover(ispresented:ondismiss:content:)))
- **Popovers:** not in compact width; show the content in a sheet instead ([HIG: Popovers](https://developer.apple.com/design/human-interface-guidelines/popovers))
- **Input:** touch. Controls in the middle and lower part of the screen are easier to reach, which makes swiping back and swipe actions on list rows important ([HIG: Designing for iOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-ios))

## iPhone Duo

iPhone Duo is still an iPhone: the iPhone patterns above apply, on an outer display and a larger inner display that can be closed, open or partly folded ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)). Standard components and a layout that resizes adapt on their own. Technique and APIs: `swift:swiftui` → `iphone-duo.md`.

- **One app, every pose:** use size classes, layout margins and safe areas, with no fixed widths and nothing tied to one display, and let the existing layout expand into the space it gets instead of designing a layout per pose. When the fold forces a change, move only what is needed and keep controls recognisable, since controls that vanish or jump are hard to find again ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Same functionality, one more level:** keep functionality, state and the information hierarchy the same on both displays. The inner display may show one more level of that hierarchy, as Mail shows either the message list or a message when closed and both side by side when open, but never a different app. Every control and piece of content stays reachable in every pose ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Split views:** a split view expands on the inner display and collapses to one pane on the outer display, and its column widths and margins follow the fold by themselves; prefer it, or another system container, to a hand-built two-pane layout ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Arrangement views:** a layout that already places two views side by side, one above the other, or one over the other can use an arrangement view, which only lays out content: the tab view or navigation container goes around it, never inside it ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)); choice and API: `iphone-duo.md`
- **Bars at the side:** on the outer display, and on the inner display in landscape, the toolbar, tab bar, navigation buttons, status bar and Dynamic Island sit along a side edge; on the inner display in portrait the bars stay horizontal. Use the system bars and leave their placement at the default, because the vertical position of controls is a core iPhone Duo pattern ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Asymmetry:** controls sit on one edge, and in Split View each app puts its controls on its outer edge, so the space beside the content differs from side to side. Safe areas keep controls off the content, those on the opposite edge included ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)); the safe-area rules are in `hierarchy-layout.md` → Margins and Safe Areas
- **Same controls in every pose:** not every pose puts controls at the side, so keep their relative positions as similar as possible, and people will not relearn where actions live ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Toolbar order:** the top of the vertical bar holds primary navigation (Back or Close), then prominent actions such as Done; the other items keep their groups, and the system adds space between the groups from the top and bottom bars ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Overflow priority:** items overflow from bottom to top. Give the actions people use most (Compose in Mail, New Note in Notes) and any item that shows status, such as a badge, a higher visibility priority, for whole groups first and then for single items ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)); code: `toolbar-patterns.md` → SDK 27 overflow and visibility
- **Groups, not spacing:** group related items with the system group types and add no fixed spacing by hand, so the system spaces them and adapts as room changes ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Title and symbol:** every toolbar item that is not text-only has both, because the system shows the title in overflow menus and expanded forms. Text labels stay in a horizontal bar, so prefer a symbol where one works ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Overflow menu:** put the app's own overflow actions in the system overflow menu, so everything is in one place. The ellipsis symbol is for overflow only; any other menu gets a distinct symbol ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Tight space:** a browsing screen keeps the tab bar and moves toolbar items into overflow, which is the default; a task screen (compose, edit) keeps its toolbar actions and lets the tab bar minimise ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)); code: `toolbar-patterns.md` → Adaptive vertical bars
- **Controls beside their content:** controls that act on one pane stay with that pane, above it, and not in the side bar that serves the other pane; in Mail, the controls for the message list stay above the list ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Full width:** a visual screen that does not scroll and needs no bars, such as a calculator, can span the full display width as long as nothing meets the Dynamic Island or the status bar. A background or header may run edge to edge while scrolling content stays inset ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))
- **Fold and cameras:** content avoids three reserved regions: the outer camera, always there and growing into the Dynamic Island for Live Activities; the inner camera, only while it is on; and the fold, only when the device is partly open. Many system components adapt by themselves: sheets, alerts and context menus move clear of the fold, and split views adjust their column widths and margins ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)); the grid and centre-band rules are in `hierarchy-layout.md` → Margins and Safe Areas
- **Games:** playable in every pose, filling the screen, with steady text and control sizes, and a changing aspect ratio instead of letterboxing ([HIG: Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo))

## iPad

- **Navigation:** a tab bar at the top of the screen, fixed or with a button that turns it into a sidebar (`sidebarAdaptable`). Lead with the tab bar and offer the sidebar when the app has more areas than fit; a sidebar without the tab bar option is a `NavigationSplitView` ([HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars), [HIG: Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)). If people can customise the tabs, start them with five or fewer ([HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars))
- **Sidebars and split views:** a sidebar shows two levels at most; deeper data gets a split view with a content column between sidebar and detail ([HIG: Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)). Show the sidebar by default and let people hide it with the edge swipe ([HIG: Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)). Windows resize freely, so lay out the two or three panes for narrow, compact and in-between widths, with a clear path between panes at each ([HIG: Split views](https://developer.apple.com/design/human-interface-guidelines/split-views), [Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass))
- **Toolbars:** the toolbar can share the top row with the tab bar ([HIG: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)). Offer customisation in apps with many actions or long sessions; the system adds an overflow menu when items don't fit, so don't build one ([HIG: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)). In a windowed app, the window controls appear at the toolbar's leading edge, so move leading buttons inward while they show ([HIG: Windows](https://developer.apple.com/design/human-interface-guidelines/windows))
- **Inspectors:** a trailing column in regular width and a sheet in compact width ([SwiftUI: inspector(isPresented:content:)](https://developer.apple.com/documentation/swiftui/view/inspector(ispresented:content:))), opened from a button at the trailing end of the toolbar ([HIG: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)); see `sheet-navigation-patterns.md` → Inspector
- **Sheets and windows:** give the large display to content, with few modal views and full-screen transitions ([HIG: Designing for iPadOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-ipados)); sheets use the page or form style ([HIG: Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets)). A task that works best beside the rest of the app, like writing a new message in Mail, can open its own window, but windows aren't the default; put a command for it in a context menu or the File menu instead ([HIG: Windows](https://developer.apple.com/design/human-interface-guidelines/windows))
- **Pointer:** a trackpad or mouse adds to touch rather than replacing it ([HIG: Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices)). Standard controls get the system pointer effects. For a custom element, highlight suits a small element with a transparent background, lift a small one with an opaque background, and hover a large one; skip effects that are only decoration ([HIG: Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices)). The modifier is `hoverEffect(_:isEnabled:)` (`visionos.md` → Input and hover)
- **Keyboard:** iPad apps now get a menu bar too, for quick access to common commands ([Adopting Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass)), and holding Command lists the commands that have shortcuts ([SwiftUI: commands(content:)](https://developer.apple.com/documentation/swiftui/scene/commands(content:))). Leave buttons, segmented controls and switches to Full Keyboard Access instead of building keyboard navigation for them ([HIG: Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards))

## Mac

- **Navigation:** a sidebar on the leading side, from `NavigationSplitView` or from `sidebarAdaptable`, which always shows a sidebar on macOS ([HIG: Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars), [SwiftUI: sidebarAdaptable](https://developer.apple.com/documentation/swiftui/tabviewstyle/sidebaradaptable)). Let people show and hide it with a button and with View menu commands, collapse it on its own when the window gets narrow, and keep critical items away from its bottom, which a window dragged low can hide ([HIG: Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)). Use the large display to show more content in fewer levels, with less modality ([HIG: Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos))
- **Toolbars:** the toolbar sits in the window frame, and its items have no bezels. Every toolbar item also exists as a menu bar command, because people can hide or customise the toolbar. Title the window with a short name for its content, never the app's name ([HIG: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)). The primary action appears as a prominent text button ([WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/))
- **Inspectors:** an inspector shows the current selection and follows it as it changes; put it in the trailing pane of a split view or in a panel. A window whose content stays put when the selection changes is an Info window, which is a regular window ([HIG: Panels](https://developer.apple.com/design/human-interface-guidelines/panels), [HIG: Split views](https://developer.apple.com/design/human-interface-guidelines/split-views)). A dense inspector can use smaller controls with `controlSize(_:)`; mini, small and medium controls keep rounded rectangles for density ([WWDC25 323](https://developer.apple.com/videos/play/wwdc2025/323/), [WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/)). `InspectorCommands` adds a menu command that toggles the inspector with Control-Command-I ([SwiftUI: InspectorCommands](https://developer.apple.com/documentation/swiftui/inspectorcommands))
- **Sheets, windows and panels:** a sheet dims and blocks only its parent window, so people can still use other windows; give it a sensible default size. A self-contained task such as editing a document gets its own window, media can go full screen, and input people repeat while checking each result, like find and replace, goes in a panel ([HIG: Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets)). Open windows when they help, not by default, and never draw custom window frames or controls ([HIG: Windows](https://developer.apple.com/design/human-interface-guidelines/windows)); the `openWindow` environment action opens one ([SwiftUI: openWindow](https://developer.apple.com/documentation/swiftui/environmentvalues/openwindow))
- **Bottom bar:** only for a little status information about the window's content; anything more belongs in an inspector ([HIG: Windows](https://developer.apple.com/design/human-interface-guidelines/windows))
- **Pointer and keyboard:** people expect precise pointer selection and editing, keyboard shortcuts, and every command in the menu bar ([HIG: Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos)). Don't redefine system trackpad gestures ([HIG: Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices)). Keep standard shortcuts for their standard actions, add custom ones only for the most frequent commands, and write modifiers in the order Control, Option, Shift, Command ([HIG: Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)). The scene's `.commands` become menu bar menus on macOS, and `keyboardShortcut(_:modifiers:)` gives a control its shortcut ([SwiftUI: commands(content:)](https://developer.apple.com/documentation/swiftui/scene/commands(content:)), [SwiftUI: keyboardShortcut(_:modifiers:)](https://developer.apple.com/documentation/swiftui/view/keyboardshortcut(_:modifiers:))); code in `macos-window-styling.md` → Commands & Keyboard

## Vision Pro

- **Navigation:** the tab bar is vertical and fixed beside the window's leading edge, and it expands when people look at it. Give every tab a symbol and a short label ([HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)). For a deep hierarchy, put a sidebar inside a tab, and don't let a sidebar selection switch tabs ([HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars), [HIG: Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars))
- **Toolbars:** the system toolbar runs along the window's bottom edge, slightly in front of it. Use it rather than your own, never make a vertical toolbar (tab bars are the vertical ones), keep the window from shrinking narrower than the toolbar, since there is no menu bar, and avoid pull-down menus in it ([HIG: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)). A custom ornament is only for controls or information people need often, in one fixed place beside the window: keep it visible, no wider than its window, and keep the number of ornaments low ([HIG: Ornaments](https://developer.apple.com/design/human-interface-guidelines/ornaments)); the API is in `visionos.md` → Floating controls
- **Supplementary content:** `inspector(isPresented:content:)` doesn't exist on visionOS ([SwiftUI: inspector(isPresented:content:)](https://developer.apple.com/documentation/swiftui/view/inspector(ispresented:content:))). Show supplementary information in a split view rather than a new window ([HIG: Split views](https://developer.apple.com/design/human-interface-guidelines/split-views), [HIG: Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets))
- **Sheets and windows:** a sheet floats in front of its window and dims it; centre it in the person's field of view rather than raising it from the window's bottom edge, and don't let it cover most of the window ([HIG: Sheets](https://developer.apple.com/design/human-interface-guidelines/sheets)). Familiar, UI-centred tasks go in windows. A new window is 1280x720 pt unless you set a size, so choose an initial size and shape that leave little empty space ([HIG: Windows](https://developer.apple.com/design/human-interface-guidelines/windows)). Bounded 3D content goes in a volume, and each moment gets the least immersion that serves it ([HIG: Designing for visionOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-visionos)); scene types: `visionos.md` → Windows, volumes and immersive spaces
- **Input:** people aim with their eyes and tap with a hand at rest; direct touch is for content within reach and for short interactions ([HIG: Designing for visionOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-visionos)). People can attach a trackpad, mouse or keyboard and keep using eyes and hands; focus moves to whatever sits beneath the pointer without any app code ([HIG: Pointing devices](https://developer.apple.com/design/human-interface-guidelines/pointing-devices)). Holding Command shows the app's shortcuts in one flat list, so each shortcut title has to make sense without a submenu around it ([HIG: Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards))
- **Comfort:** keep interface elements in the field of view, prefer wide layouts to tall ones, and don't anchor content to the wearer's head ([HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)); motion in `motion.md`
